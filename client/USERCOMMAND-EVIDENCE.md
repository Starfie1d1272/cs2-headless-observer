## 结果

- 玩家指令处理函数 0x180b7ae90 首先调用 0x180b61610 解码列表，随后检查各条指令的数据存在标记。
- 解码时，消息带 delta-data 标记而对应玩家缓存的完整指令序号（上下文 +0x5920）为零，会输出 Missing command to delta from，跳过该条增量恢复。
- 后续处理仍检查 command-data 标记，缺失时输出 with no command data。因此两条警告可由同一条未恢复的增量指令连续产生，不证明服务器发送了空数据，也不能仅凭文字断言网络丢包。
- 非增量且具有完整 command-data 的分支更新缓存内容和序号。0x180944530 / 0x1809446c0 在首次创建对应玩家上下文时将序号初始化为零；已存在上下文不会在每次查询时清零。
- 通过 PE exception directory 的 chained unwind 还原函数起点；0x180b61639 和 0x180b7aec4 是片段起点，不能当作完整函数入口。完整入口及调用关系已重新核对。
- 指令列表逐项检查解释了重复输出速度可能很高；没有从截图估算实际条数或性能损耗。

## 与 Mizar 和当前无头客户端的关系

v1.5.0 的 Mizar 观战 CFG 只设置数字键观战切人，未见 cl_predict、cl_interp 或玩家指令 delta 参数。启动会改变窗口、画质/FPS、worldwide，并可请求 condebug；尚无直接因果证据，仍需对照启动方式、来源与初始化时序，不能据此排除间接影响。

这里的玩家操作指令缓存与实体 PacketEntities 基线不同。本客户端以实体和游戏事件输出火力/击杀/回合事件；不能把实体基线修复说成已经解决官方客户端这两条 UserCommands 警告。

## 离线对照补充

同一固定公开 Demo（SHA-256 143eb78444727c7a8afa29d807272076d14044fc9d7c233035d0b9a176e70f60）逐包统计：185,932 个包，1,857,826 条 UserCommands 消息，其中完整数据 3,905 条、增量 1,853,921 条。10 个玩家槽位首次均在 tick 1380 出现完整数据，未发现首次完整数据之前的增量。完整数据后续出现间隔不规则；这份文件不是故障场次，也不能作为完美 GOTV 初始化正常的证据。

进一步静态核对发现解码还有玩家实体存在性条件：完整数据到达时，如果玩家实体尚未可查，该条不会建立对应缓存。因此下一轮有效现场证据需要同时看完整指令与玩家实体建立顺序，不能仅统计网络是否收到完整消息。

Mizar 当前控制台采集在独立工作线程每秒轮询，单次原文件读取预算 256 KiB；不写回或截断游戏 console.log。启用 condebug 后游戏自身写日志的成本仍需现场测量，不能从读取预算推导没有性能影响。
