# 2026-10-24 Windows 真实普通观众验证

本机 Steam/App730，CS2 build 10955、host protocol 14192、Inferno；原生桥 ABI3，
有序解析 IPC3。观察者包基线为 dc3c262c，使用独立候选源码覆盖做私有兼容性实验。
现有生产 CLI 的 14191 版本门禁没有扩大，未来事件未进入公开 HUD、OBS 或网站。

## 已复现并修正

- 初始 SpawnGroup Load 已携带 creation sequence，但驱动只在后续 SetCreationTick
  才推进解析器水位。真实加入流程没有该后续消息，第一份实体快照因此被拒绝。
  现在使用 Load 的权威序号，并继续独立验证 manifest、父依赖和世界准备状态。
- 普通观众 userinfo 未声明 rate。原候选首快照后停止收数；声明本接收器拥有的
  786432 bytes/s 预算后，第一份完整快照在约一秒内提交并持续收到增量实体和事件。
- GNS 会将过大的不可靠消息升级为可靠传输，内层 tag4 仍保留原序号头。
  原来强制两层可靠性相等，在真实 39697-byte 消息处退出。现在仍拒绝可靠内层
  落在不可靠传输上，但允许 SDK 升级；顺序过滤和消息上下文取内层头的类型。
  参考 [Valve SNP 实现](https://github.com/ValveSoftware/GameNetworkingSockets/blob/master/src/steamnetworkingsockets/clientlib/steamnetworkingsockets_snp.cpp)。
- 实体整数解码保留 bigint，投影只接受 number，使回合和压缩 pawn 字段失效。
  仅在投影边界将 uint32 范围内的整数转为 number，Steam64 与完整 native handle
  序号比较仍保持原精度和拒绝条件。

## 实际证据与限制

两路授权普通观众源分别持续采集 300 秒；早源解析到 21 次击杀、619 次开火，
延迟源 16 次击杀、485 次开火。收到并恢复过快照依赖缺失；这不是无间断稳定性通过。
另一轮按同一事件 server tick 和全部原始事件字段匹配 7 次击杀，接收时间差中位数
120.013 秒，范围 119.799–120.031 秒。它证明这两路事件接收间隔，不等于 OBS
实际画面时间校准。

当前仍有真实身份边界未闭合：事件 pawn 完整 17-bit serial 与接收实体的 serial
不一致，即使低 10 位相同也保持未知，不截短序号来制造通过。controller Steam64
与 userinfo 可互证，仍不足以宣称原有严格 pawn 关联通过。新地图、完整重连、
14192 正式支持、Mizar 私有接线也未由这份证据自动验收。

官方正常 CS2（未加载 MulNX）在这两路均持续出现 UserCommands 无完整数据／缺失
delta 基线的控制台警告。44 秒原始流中 27680 条命令，48 条带完整 data，27632 条
带 delta_data；delta 本身不是损坏证明。接收端缓存为何没有对应基线仍需继续分析。
不能把该警告直接归为 Mizar、HUD 或实体事件解析失败。

原始样本仅保存在用户本机，含玩家身份与比赛资料，不提交到公开仓库。通道采集器
只在认证结束并验证应用头后写入，不记录密码、握手或 Steam 票据。

## 无比赛时重放

`replay_ordered.py` 使用相同有序解析器重放原始 SDK 通道采样，不初始化 Steam，
不连接服务器，不发送应答；输入保留的相对时间和来源文件 hash 会写入报告。

```powershell
python client/replay_ordered.py --input <private-channel.frames> `
  --worker <candidate-parser_worker.mjs> --node <node.exe> `
  --host-version 14192 --output <new-output-directory>
```

离线完成只能证明所录字节可重复解析，不能替代新的认证、在线接入或重连验收。
采样含故障就保留故障，不以文件存在、计数增加或离线完成宣称线上全部通过。

## 有界历史缓存的后续回归

继续采集发现，多次缺口恰好引用129–134帧以前的历史，而默认缓存只有128帧。
仅保护一帧当前基线仍会淘汰下一次即将引用的旧帧；同一真实流回放证明这不足以修复。
候选将默认历史预算调整为512帧，并在预算淘汰时保留当前引用基线和最新帧，
让长时间重复引用同一基线也不丢失依据。上限仍然有界；512是本地资源策略，
不是宣称服务器协议只允许这一范围。引用确实不在缓存时仍拒绝、恢复并停止有效提示。

同一份300秒、38168帧真实早源采样，候选完整回放保留21次击杀与620次原始开火，
生成300个cursor；仅剩初始ClearStringTables边界，两个Missing snapshot缺口不再出现。
44项独立快照事务断言覆盖了持续引用旧基线、134帧滞后、预算淘汰、基线推进及
真正缺失时仍拒绝等情况。此处只记录离线候选证据；当前比赛的连续采集仍保持原候选，
没有在半场热替换解析器或把离线结果冒充新版本实机通过。

## 第二场热身到开局

随后在新授权的 Dust2 早源与延迟源各持续接收600秒，使用512帧缓存候选。
两路均只有加入时的ClearStringTables边界，没有Missing snapshot恢复；
原始应用通道分别为89154680和87524843字节，SHA-256保存在本机索引。
未录屏，原始通道不是原生Demo。热身状态退出、begin_new_match（tick24900）、
round_announce_match_start及首回合round_freeze_end（tick26595）均有实际数据。

发现Python输出白名单只包含旧round_start/round_end，过滤了当前源实际发送的
开局、冻结期结束和比赛结束原始事件。补齐明确的生命周期事件转发；不改名，
不合成round_start，不从热身回合事件推导正式比赛开始，也不改变事件和传输tick
的不同语义。事件仍携带原始eventServerTick、committedTick和来源世界身份。

两路原始通道按事件名、server tick及完整原始字段匹配79条事件，其中51次击杀。
正式开局后42条匹配事件的估算接收间隔为119.991–120.012秒，中位120.0035秒。
热身末段曾缩短到114.050秒；不能将整段写死为120秒或宣称已经完成画面时间校准。
通道文件仅保存单调相对时间，Unix锚点由输出事件的最小处理延迟估计，另有最多
14毫秒的相对输出处理延迟；上述结果用于研究比较，不是精确SDK墙钟采样。

延迟源在重叠范围内没有13条早源已有的round_prestart/poststart/officially_ended；
应保留源间事件覆盖差异，不能靠两路逐项事件一一对应作为持续运行的前提。
原始数据、配对结果与丢失项均留在用户本机，不提交比赛身份或观战凭据。
